1. INTRODUCTION & OVERVIEW: WHAT ARE THESE TOPICS?
================================================================================

This document provides a comprehensive theoretical exploration of clock generation,
timing synchronization, and multi-cycle execution implemented in Version 3.1:

1. The Physical Clock Generator (`ClockGenerator`):
   The electronic heartbeat of the microprocessor. A quartz crystal oscillator
   that emits a continuous, periodic train of square-wave voltage pulses, defining
   the discrete time quanta in which all physical computing occurs.

2. Multi-Cycle CPU Architecture:
   A micro-architecture where instruction execution is partitioned into a sequence
   of discrete, uniform micro-operations ($\mu\text{Ops}$), each requiring exactly ONE
   physical clock cycle to complete.

3. Two Operational Granularities:
   • Micro-Stepping (`vm.tick()`): Advancing the CPU by a single physical clock cycle
     to observe internal bus transitions, latch updates, and intermediate micro-states.
   • Macro-Stepping (`vm.step()`): Executing multiple clock cycles until the current
     instruction completes its entire sequence of micro-operations.

2. THE MOTIVATING PROBLEM: WHY DO CLOCK DOMAINS & MULTI-CYCLE EXECUTION EXIST?
================================================================================

In software simulators, it is tempting to believe that an instruction executes
"instantly":
    `function step() { fetch(); decode(); execute(); memory(); writeBack(); }`
Everything appears to happen in zero time during a single JavaScript function call.

In physical reality, **NOTHING HAPPENS INSTANTANEOUSLY IN SILICON**:

1. Finite Electron Propagation Speed:
   Electrons travel through metallic traces and semiconductor silicon at roughly
   $10^7 \text{ meters/second}$ to $10^8 \text{ meters/second}$ (a fraction of the
   speed of light). Signals require real physical picoseconds and nanoseconds to
   travel across the chip die.

2. Gate Switching Latencies (Propagation Delay $t_{pd}$):
   Every transistor gate acts as a microscopic capacitor that must be electrically
   charged and discharged. When an input changes, the output takes a finite amount of
   time ($t_{pd}$) to transition from LOW to HIGH. In a 16-bit ripple-carry adder,
   the carry bit must ripple through 16 consecutive full adders, accumulating delay.

3. Memory Bus Access Latency:
   Accessing external RAM requires leaving the CPU chip, driving motherboard PCB traces,
   waiting for the DRAM/SRAM chip decoders to stabilize, and driving data back into the
   processor. Memory access is hundreds of times slower than an internal register read!

THE FATAL FLAW OF THE SINGLE-CYCLE ARCHITECTURE:
If a processor executes an entire instruction in a single clock cycle, the clock
period ($T_{clk}$) MUST be lengthened to accommodate the SLOWEST possible instruction
in the entire instruction set (the "Critical Path"):
  $T_{clk} \ge t_{Fetch} + t_{Decode} + t_{AddressCalc} + t_{RAM\_Access} + t_{WriteBack}$

If a memory load takes 6 nanoseconds, the clock must run at:
  $f = \frac{1}{6\text{ ns}} \approx 166\text{ MHz}$
Even when executing a simple instruction like `ADD R0, R1, R2` (which only takes
1 nanosecond), the single-cycle CPU MUST waste 5 nanoseconds doing absolutely
nothing, waiting for the unnecessarily long clock period to finish!

THE HARDWARE SOLUTION: MULTI-CYCLE ARCHITECTURE
Instead of one massive, sluggish clock cycle:
  • The clock is made FAST and UNIFORM (e.g. 1 nanosecond per tick).
  • Long instructions take multiple ticks (e.g., `LD` takes 6 ticks).
  • Fast instructions finish early and start the next instruction immediately
    (e.g., `ADD` finishes in 5 ticks).
  • Hardware functional units (like the ALU and Memory Bus) can be reused across
    different clock cycles within the SAME instruction, saving enormous silicon area!

3. IN-DEPTH PHYSICAL & ELECTRICAL THEORY
================================================================================

--------------------------------------------------------------------------------
A. THE PIEZOELECTRIC QUARTZ CRYSTAL OSCILLATOR
--------------------------------------------------------------------------------
How is a digital clock physically generated?
Computers utilize the **Piezoelectric Effect** discovered in natural quartz ($SiO_2$):
  1. A microscopic sliver of quartz crystal is cut to precise physical dimensions.
  2. When an alternating electric field is applied, the crystal vibrates mechanically.
  3. Because of its mechanical resonance, it vibrates at an extraordinarily precise,
     temperature-stable frequency (e.g., 14.318 MHz, 20 MHz, 100 MHz).
  4. An amplifier circuit sustains this mechanical vibration, and a Schmitt Trigger
     circuit squares the sinusoidal waves into crisp digital HIGH and LOW voltages:
```
           +5V ──┐         ┌───┐         ┌───┐
                 │         │   │         │   │
            0V ──┴─────────┘   └─────────┘   └─────────
                 ◄──── T ────►
```

--------------------------------------------------------------------------------
B. CLOCK CHARACTERISTICS & DEFINITIONS
--------------------------------------------------------------------------------
1. Clock Period ($T$):
   The duration of one complete cycle (from one rising edge to the next). Measured
   in seconds (typically nanoseconds, $1\text{ ns} = 10^{-9}\text{ s}$).
2. Clock Frequency ($f$):
   The number of cycles per second:
                         f = 1 / T  (Hertz / MHz / GHz)
   If $T = 1\text{ ns}$, frequency $f = 1\text{ GHz}$.
3. Clock Edges:
   • Rising Edge (Low-to-High transition): When most state elements latch data.
   • Falling Edge (High-to-Low transition): Used in two-phase clocking or master-slave latches.
4. Setup Time ($t_{setup}$) & Hold Time ($t_{hold}$):
   • $t_{setup}$: Input data must remain completely stable BEFORE the rising edge.
   • $t_{hold}$ : Input data must remain stable AFTER the rising edge.
   Clocking ensures inputs stabilize before latches sample them, eliminating race conditions.

--------------------------------------------------------------------------------
C. THE CPU PERFORMANCE EQUATION & CPI
--------------------------------------------------------------------------------
Computer performance is mathematically governed by the classic Iron Law of Processor
Performance:

       Execution Time = (Instruction Count) * (CPI) * (Clock Period T)

Where:
  • **Instruction Count (IC)**: Number of instructions in the program.
  • **CPI (Cycles Per Instruction)**: The average number of clock cycles required
    to execute an instruction.
  • **Clock Period (T)**: Time per physical clock tick.

In Version 3.1:
  • `ADD` takes **5 clock cycles**.
  • `LD` takes **6 clock cycles**.
  For our 5-instruction program (2 `LD`s and 3 `ADD`s):
       Total Cycles = (2 * 6) + (3 * 5) = 12 + 15 = 27 cycles
       Average CPI = 27 cycles / 5 instructions = 5.40 CPI

B. MICRO-SEQUENCER FINITE STATE MACHINE (FSM)
--------------------------------------------------------------------------------
A hardware State Register tracks which clock cycle the CPU is currently executing:

```
                ┌───────────────────────────────────────┐
                │          STATE 1 (Clock 1)            │
                │ FETCH-1: GatePC=1, LD_MAR=1, MemRead=1│
                └───────────────────┬───────────────────┘
                                    │ Clock Pulse
                                    ▼
                ┌───────────────────────────────────────┐
                │          STATE 2 (Clock 2)            │
                │ FETCH-2: RAM[MAR] -> Data Bus -> MDR  │
                └───────────────────┬───────────────────┘
                                    │ Clock Pulse
                                    ▼
                ┌───────────────────────────────────────┐
                │          STATE 3 (Clock 3)            │
                │ FETCH-3: GateMDR=1, LD_IR=1, PC <=PC+1│
                └───────────────────┬───────────────────┘
                                    │ Clock Pulse
                                    ▼
                ┌───────────────────────────────────────┐
                │          STATE 4 (Clock 4)            │
                │ DECODE: PLA Decode, RegFile Read, SEXT│
                └───────────────────┬───────────────────┘
                                    │
                  ┌─────────────────┴─────────────────┐
     Opcode = ADD │                                   │ Opcode = LD
                  ▼                                   ▼
┌───────────────────────────────────┐ ┌───────────────────────────────────┐
│         STATE 5A (Clock 5)        │ │         STATE 5B (Clock 5)        │
│ EXECUTE & WB:                     │ │ EXECUTE:                          │
│ ALU Compute, GateALU=1,           │ │ Effective Address = PC + Offset,  │
│ LD_REG=1, LD_CC=1                 │ │ GateMARMUX=1, LD_MAR=1, MemRead=1 │
└─────────────────┬─────────────────┘ └─────────────────┬─────────────────┘
                  │                                     │ Clock Pulse
                  │ Instruction Complete                ▼
                  │ (5 Cycles Total)  ┌───────────────────────────────────┐
                  │                   │         STATE 6 (Clock 6)         │
                  │                   │ MEMORY & WB:                      │
                  │                   │ RAM -> MDR, GateMDR=1,            │
                  │                   │ LD_REG=1, LD_CC=1                 │
                  │                   └─────────────────┬─────────────────┘
                  │                                     │
                  │                                     │ Instruction Complete
                  │                                     │ (6 Cycles Total)
                  ▼                                     ▼
         [Branch back to STATE 1 for Next Sequential Instruction]
```

5. HOW THESE CONCEPTS ASSIST PROGRAM EXECUTION & RELIABILITY
================================================================================

1. Deterministic Instruction Latency:
   In real-time systems (such as medical devices, flight controllers, automotive
   ECUs), programmers must know EXACTLY how many clock cycles a loop takes to execute
   to maintain synchronization with external sensors.

2. Glitch-Free Electrical Stabilization:
   By allowing intermediate combinational logic (ALU additions, address decoders)
   an entire clock cycle to settle before latching, the system is immune to transient
   signal glitches (metastability).

3. Foundations for Advanced Architectures:
   Understanding multi-cycle micro-stepping is the direct prerequisite to:
     • Pipelining (overlapping these independent clock states across multiple instructions).
     • Superscalar execution (multiple ALUs executing micro-ops concurrently).
     • Interrupt Handling (checking for external hardware interrupt pins at the boundary
       between the final micro-cycle and State 1).

6. IMPLEMENTATION IN VERSION 3.1 CODEBASE
================================================================================

--------------------------------------------------------------------------------
A. `src/version3.1/src/clock/clock-generator.js`
--------------------------------------------------------------------------------
Encapsulates the physical quartz oscillator:
  • `this.cycleCount`: Running integer tracking total elapsed clock cycles.
  • `this.signal`: Voltage level (0 or 1).
  • `this.phase`: 'RISING' / 'LOW' edge indicator.
  • `tick()`: Advances the oscillator by exactly 1 physical clock pulse.

--------------------------------------------------------------------------------
B. `src/version3.1/src/cpu/cpu-pipeline.js`
--------------------------------------------------------------------------------
Contains the micro-sequencer state machine (`this.microStep`):
  • `microStep === 1`: `FETCH-1` (GatePC -> BUS -> MAR, MemRead asserted).
  • `microStep === 2`: `FETCH-2` (Memory read latency -> MDR latches data bus).
  • `microStep === 3`: `FETCH-3` (GateMDR -> BUS -> IR, PC incremented).
  • `microStep === 4`: `DECODE`  (IR field decode, RegFile read, SEXT).
  • `microStep === 5`: `EXECUTE` (ALU compute & write-back for ADD [Finishes in 5 cycles];
                                 Address calculation & MAR latch for LD [Advances to 6]).
  • `microStep === 6`: `MEM & WB` (RAM read -> MDR -> BUS -> RegFile[DR], LD_CC [Finishes in 6 cycles]).

--------------------------------------------------------------------------------
C. `src/version3.1/src/vm.js`: Dual Operational Granularities
--------------------------------------------------------------------------------
Exposes two distinct execution functions:
  1. `vm.tick()`:
     Pushes the clock by one tick. Executes a single micro-operation.
     Returns `{ cycle, microOp, instructionComplete, events, busState }`.
  2. `vm.step()`:
     Repeatedly calls `vm.tick()` until `instructionComplete === true`.
     Returns `{ cyclesTaken, pc, decoded, execution, description }`.

--------------------------------------------------------------------------------
D. Step Description & Telemetry Output
--------------------------------------------------------------------------------
When running programs via `vm.step()` or `vm.run({ verbose: true })`, the user sees:
  `Clock Execution Timing : 6 Clock Cycles (Total CPU Cycles Elapsed: 12)`
  `Hardware Datapath & Storage Workflow :`
  `  • [Clock 7  | FETCH-1: Drive PC to MAR] Central Internal Bus: GatePC=1 -> BUS <= PC (12289)`
  `  • [Clock 8  | FETCH-2: Memory Read into MDR] External Memory Bus: MDR <= 0x2404`
  `  • [Clock 9  | FETCH-3: Latch IR & Increment PC] GateMDR=1 -> BUS <= MDR -> IR <= BUS`
  `  • [Clock 10 | DECODE: Unpack Fields & Read Registers] Control Unit & SEXT`
  `  • [Clock 11 | EXECUTE: Address Calculation & MAR Latch] GateMARMUX=1 -> MAR <= BUS`
  `  • [Clock 12 | MEMORY & WB: Read RAM & Latch Register] GateMDR=1 -> R2 <= BUS, PSR <= [N]`
