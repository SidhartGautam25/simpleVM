1. INTRODUCTION & OVERVIEW: WHAT ARE THESE TOPICS?
================================================================================

In a microprocessor, the Datapath (registers, Arithmetic Logic Unit, internal
buses, latches, and memory interfaces) provides the raw physical hardware capable
of moving and calculating data. However, the Datapath is completely inert on its
own. It cannot perform any work without external control signals telling it:
  • Which register should drive its contents onto the bus (GatePC, GateALU, GateMDR)?
  • Which latches or registers should capture the bus on the clock edge (LD.MAR, LD.IR, LD.REG)?
  • What operation the ALU should compute (ADD, PASS, NOT)?
  • Whether memory should perform a read or write operation (MemRead, MemWrite)?

The electronic brain responsible for orchestrating these signals at every single
clock cycle is the CONTROL UNIT.

In Version 3.2, we introduce the authentic, textbook computer architecture standard
for implementing the Control Unit: the MICROCODED FINITE STATE MACHINE (FSM)
CONTROL SEQUENCER.

Key Components Introduced:
1. Micro-Program Counter (uPC):
   A dedicated internal register inside the control unit that holds the memory
   address of the micro-instruction currently being executed within the Control
   Store ROM.

2. Control Store Read-Only Memory (ROM):
   A specialized, high-speed on-chip memory array that contains the entire micro-
   program of the processor. Each word in this ROM is a "Micro-Instruction" that
   explicitly encodes the control wire assertions and next-state transition logic
   for exactly one clock cycle.

3. Next-Address Generation Logic:
   Dedicated combinational logic and multiplexers that compute the next value of
   the uPC based on unconditional jumps, opcode decoding (branching to different
   execution paths based on IR[15:12]), or arithmetic status flags (NZP condition
   codes).

4. Micro-Branching:
   The capability of the microsequencer to dynamically alter its execution path
   through the Control Store ROM based on the instruction register's opcode or
   external condition signals, routing the CPU seamlessly from common fetch states
   into opcode-specific execution states.

2. THE MOTIVATING PROBLEM: WHY DO MICROPROGRAMMED CONTROL SEQUENCERS EXIST?
================================================================================

--------------------------------------------------------------------------------
A. The Hardwired Control Nightmare (Random Logic & Combinational Explosion)
--------------------------------------------------------------------------------
In early computing and pure RISC designs, the control unit was constructed as a
"Hardwired Control Unit." In a hardwired control unit, control signals are generated
by massive networks of discrete combinational logic gates (AND, OR, NOT gates, or
Programmable Logic Arrays - PLAs) connected to a ring counter:

               +-----------------------+
   Opcode ---->| Combinational Logic   |----> GatePC
   Clock  ---->| (Hundreds of discrete |----> LD.MAR
   Flags  ---->|  gates / Karnaugh     |----> MemRead
               |  minimized formulas)  |----> LD.IR
               +-----------------------+

While hardwired control units can be extremely fast (operating at the maximum
speed of silicon gate delays), they suffer from severe design flaws:
1. Combinational Spaghetti: As the instruction set grows (from 5 instructions to
   50 or 500), the boolean equations for every single control wire become
   monstrously complex. A change to one instruction can require redesigning the
   entire gate array.
2. High Defect Rate: Any bug in a hardwired state machine requires scrapping the
   entire physical silicon mask and re-fabricating the integrated circuit (costing
   millions of dollars and months of delay).
3. Routing Congestion: Routing thousands of individual logic wires across a chip
   creates massive propagation delay skew and consumes precious silicon die area.

--------------------------------------------------------------------------------
B. The Need for Instruction Set Extensibility and Reconfigurability
--------------------------------------------------------------------------------
As computer systems matured in the 1950s and 1960s (culminating in machines like
the IBM System/360), computer architects needed a systematic, clean, and modular
way to build processors with complex instruction sets (CISC) without drowning in
combinational logic chaos.

Architects needed:
• A way to design different tiers of computers (cheap/slow vs. expensive/fast)
  that execute the exact same instruction set architecture (ISA).
• The ability to fix processor bugs or add instructions after the hardware datapath
  had already been finalized.

--------------------------------------------------------------------------------
C. Maurice Wilkes' Breakthrough (1951): The Microprogrammed Architecture
--------------------------------------------------------------------------------
In 1951, Professor Maurice Wilkes of Cambridge University conceived an ingenious
solution: Treat the execution of an instruction as a sequence of tiny internal
sub-programs.

Wilkes proposed:
"Instead of designing an unmaintainable maze of random logic gates, why not build
a miniature, simplified computer INSIDE the main CPU? The control signals are not
computed with boolean logic; they are stored as binary words in a tiny Read-Only
Memory (the Control Store). The Control Unit simply fetches micro-instructions
from this ROM one after another, drives the control wires directly from the ROM
data pins, and uses a Micro-Program Counter (uPC) to determine the next micro-state!"

With Wilkes' design:
• Datapath control becomes structured and table-driven.
• Adding or modifying an instruction only requires editing a line in a ROM table!
• The hardware design of the control unit remains fixed regardless of how complex
  the instruction set becomes.

--------------------------------------------------------------------------------
D. Microcode Updates and Modern Silicon Reliability
--------------------------------------------------------------------------------
In modern processors (such as Intel Core, AMD Ryzen, and IBM z/Architecture),
microprogramming remains vital. When hardware vulnerabilities like Meltdown,
Spectre, or errata in floating-point division are discovered in commercial CPUs:
• The operating system or BIOS loads a "Microcode Patch" into the CPU's on-chip
  Writable Control Store (WCS) SRAM at boot time.
• The CPU's microsequencer reroutes execution away from buggy ROM states to the
  patched WCS states.
• Critical hardware flaws are fixed entirely in the field without recalling a
  single piece of silicon!

3. IN-DEPTH PHYSICAL & MICRO-ARCHITECTURAL THEORY
================================================================================

--------------------------------------------------------------------------------
A. Dual Worlds: The Datapath vs. The Control Unit
--------------------------------------------------------------------------------
A CPU is physically divided into two fundamental sections:
1. The Datapath:
   The physical pipes, registers, and computational units where user data flows
   (PC, MAR, MDR, IR, Register File, ALU).
2. The Control Unit:
   The conductor of the orchestra. It does not manipulate user numbers; it asserts
   and deasserts binary control voltages (0V / 3.3V) that open and close the
   gates of the datapath at exact clock edges.

--------------------------------------------------------------------------------
B. Anatomy of a Microcoded Control Unit
--------------------------------------------------------------------------------
A microcoded control unit consists of four essential silicon elements:
1. Control Store ROM: An array of memory cells addressed by the uPC.
2. Micro-Instruction Register (MIR): Latches the active micro-word from the ROM.
3. Micro-Program Counter (uPC): Holds the current ROM address (e.g., 6 bits for
   64 states).
4. Next-Address Mux & Logic: Determines whether uPC becomes:
   • J (unconditional target)
   • Opcode branch (derived from IR[15:12])
   • Conditional branch (derived from ALU NZP flags or memory ready signals)

--------------------------------------------------------------------------------
C. The Control Store Read-Only Memory (ROM)
--------------------------------------------------------------------------------
The Control Store ROM is physically embedded directly next to the execution units
on the silicon die. It is addressed by an $N$-bit address (for $2^N$ micro-states).
In standard academic and historical designs like the LC-3:
• Address space: 6 bits ($2^6 = 64$ possible micro-states, numbered 0 to 63).
• Word width: Typically 30 to 45 bits wide.

Each address in the ROM corresponds to exactly ONE state of the CPU's finite
state machine, and each row is read out in exactly ONE clock cycle.

--------------------------------------------------------------------------------
D. The Micro-Program Counter (uPC) and Next-Address Logic
--------------------------------------------------------------------------------
Just as the architectural Program Counter (PC) steps through user instructions
in system RAM, the Micro-Program Counter (uPC) steps through micro-instructions
in the internal Control Store ROM.

On every rising edge of the physical clock:
  uPC <= Next_Micro_Address

How is Next_Micro_Address calculated?
  Next_Micro_Address = Multiplexer(
      Select = COND,
      Inputs = [
          J,                         (Unconditional: next state is given by J bits)
          Opcode_Dispatch(IR[15:12]),(Branch based on decoded instruction opcode)
          Memory_Ready_Check,        (Branch if memory bus assertion ready)
          ALU_Flag_Check             (Branch if Branch condition matches PSR)
      ]
  )

--------------------------------------------------------------------------------
E. Micro-Instruction Word Formats: Horizontal vs. Vertical Microcode
--------------------------------------------------------------------------------
In computer architecture, micro-instructions are designed in two styles:

1. Horizontal Microcode:
   • Every single control wire in the entire CPU has its own dedicated bit in the
     micro-word.
   • Example: Bit 0 = GatePC, Bit 1 = GateALU, Bit 2 = LD.MAR, Bit 3 = MemRead.
   • Pros: Maximum parallelism; zero decoding delay (bits connect straight to wires).
   • Cons: Very wide words (often 60 to 120 bits wide), consuming large silicon area.

2. Vertical Microcode:
   • Mutually exclusive signals are encoded into fields.
   • Example: A 3-bit "Bus Gate" field can select one of 8 bus drivers (000=None,
     001=PC, 010=ALU, 011=MDR, etc.) using a small 3-to-8 decoder.
   • Pros: Highly compact micro-words (16 to 32 bits wide).
   • Cons: Requires decoder circuits before signals reach datapath switches, adding
     a minor gate propagation delay.

Version 3.2 uses a clean, semi-horizontal structure: Control wire signals are
directly defined as active properties, paired with a Next-State Address field (J)
and a Condition Selection field (COND).

--------------------------------------------------------------------------------
F. Micro-Branching: Unconditional, Opcode Dispatch, and Status Conditioning
--------------------------------------------------------------------------------
Instruction execution is not linear. Once an instruction is fetched, the CPU must
take an entirely different physical path depending on whether the instruction is
an ADD, an LD, an AND, or a BR.

In a microcoded sequencer, this branching is performed cleanly:
1. Unconditional (`COND.UNCONDITIONAL`):
   The next micro-state is strictly defined by the micro-instruction's `nextState` (J)
   field. Example: State 18 (Fetch 1) unconditionally transitions to State 33 (Fetch 2).
2. Opcode Dispatch (`COND.BRANCH_OPCODE`):
   In State 32 (Decode), the next-address logic inspects bits [15:12] of the
   Instruction Register (IR). It maps:
     • Opcode 0001 (ADD) -> State 1
     • Opcode 0010 (LD)  -> State 2
   This single clock cycle replaces hundreds of discrete decoder logic gates!

D. Micro-Cycle Walkthrough: ADD Instruction Execution Trace
--------------------------------------------------------------------------------
Suppose the user program executes `ADD R1, R2, R3`.
Total Clock Cycles: 5 physical cycles (CPI = 5).

• Cycle 1 (uPC = 18):
  - Control ROM asserts: `GatePC = 1`, `LD.MAR = 1`, `MemRead = 1`.
  - PC drives the Global Bus; MAR latches address `0x3000`. Memory read initiated.
  - Sequencer advances: `uPC <= 33`.

• Cycle 2 (uPC = 33):
  - Control ROM asserts: `MemRead = 1`, `LD.MDR = 1`.
  - Memory responds with instruction word `0x1243`; MDR latches `0x1243`.
  - Sequencer advances: `uPC <= 35`.

• Cycle 3 (uPC = 35):
  - Control ROM asserts: `GateMDR = 1`, `LD.IR = 1`, `LD.PC = 1`.
  - MDR drives instruction onto bus; IR latches `0x1243`. PC increments to `0x3001`.
  - Sequencer advances: `uPC <= 32`.

• Cycle 4 (uPC = 32):
  - Control ROM asserts: `COND = COND.BRANCH_OPCODE`.
  - Next-Address Logic examines IR[15:12] = `0001` (ADD).
  - Target micro-address resolved to State 1.
  - Sequencer advances: `uPC <= 1`.

• Cycle 5 (uPC = 1):
  - Control ROM asserts: `GateALU = 1`, `ALUK = ADD`, `LD.REG = 1`, `DestReg = R1`.
  - ALU sums R2 and R3; result drives the bus; R1 latches the sum.
  - Instruction cycle completes! Sequencer unconditionally branches: `uPC <= 18`.

--------------------------------------------------------------------------------
E. Micro-Cycle Walkthrough: LD Instruction Execution Trace
--------------------------------------------------------------------------------
Suppose the user program executes `LD R1, [0x3005]`.
Total Clock Cycles: 6 physical cycles (CPI = 6).

• Cycles 1 to 3 (uPC = 18 -> 33 -> 35):
  - Identical fetch sequence. Instruction word `0x2205` latched into IR; PC = `0x3001`.
  - Sequencer advances: `uPC <= 32`.

• Cycle 4 (uPC = 32):
  - Control ROM asserts: `COND = COND.BRANCH_OPCODE`.
  - Next-Address Logic examines IR[15:12] = `0010` (LD).
  - Target micro-address resolved to State 2.
  - Sequencer advances: `uPC <= 2`.

• Cycle 5 (uPC = 2):
  - Control ROM asserts: `GateALU = 1`, `ALUK = ADD` (PC + offset9), `LD.MAR = 1`.
  - Effective address `0x3005` drives the bus; MAR latches `0x3005`.
  - Sequencer advances: `uPC <= 25`.

• Cycle 6 (uPC = 25):
  - Control ROM asserts: `MemRead = 1`, `LD.MDR = 1`, `GateMDR = 1`, `LD.REG = 1`.
  - RAM address `0x3005` is read into MDR, and MDR drives the bus to latch into R1.
  - Instruction cycle completes! Sequencer unconditionally branches: `uPC <= 18`.

5. HOW THESE CONCEPTS ASSIST PROGRAM EXECUTION & SYSTEM FUNCTIONALITY
================================================================================

1. Structural Modularity:
   The Control Store cleanly decouples instruction decoding logic from the datapath.
   The datapath simply responds to control wire assertions without needing to know
   which instruction is currently running.

2. Predictable Timing and Synchronization:
   Every state transition is synchronized with the physical clock generator.
   Setup times, propagation delays, and bus conflicts are guaranteed to be
   prevented because each micro-instruction strictly isolates bus drivers and
   latches.

3. Complete Transparency for Debugging:
   By externalizing the internal micro-state via the `uPC`, developers and
   system analyzers can inspect the microprocessor mid-instruction. This enables
   in-circuit emulators (ICE), JTAG hardware debuggers, and cycle-accurate
   architectural simulators.

4. Firmware Upgradability:
   Microcoded architectures allow fixing hardware bugs and updating instruction
   behavior via microcode patches without physical chip revisions.

6. IMPLEMENTATION IN VERSION 3.2 CODEBASE
================================================================================

--------------------------------------------------------------------------------
A. `cpu/micro-sequencer.js` (ROM, uPC, and Next-State Dispatch)
--------------------------------------------------------------------------------
This module encapsulates the microcoded control unit:
• `COND`: An enumeration defining branching mechanisms:
    `UNCONDITIONAL`: Next uPC is strictly `microInstruction.nextState`.
    `BRANCH_OPCODE`: Next uPC is computed by inspecting `IR[15:12]`.
• `CONTROL_STORE_ROM`: A frozen dictionary mapping integer uPC addresses
  (18, 33, 35, 32, 1, 2, 25) to immutable micro-instruction descriptor objects.
• `MicroSequencer`: A stateful class maintaining `this.uPC` (initialized to 18).
  Its `step(context)` method:
    1. Reads `this.currentMicroInstruction`.
    2. Evaluates the next state condition (`COND.BRANCH_OPCODE` or `UNCONDITIONAL`).
    3. Updates `this.uPC` to the next state on the clock transition.
    4. Returns a detailed execution trace object describing the transition.

--------------------------------------------------------------------------------
B. `cpu/cpu-pipeline.js` (Eliminating Ad-Hoc Switch Logic)
--------------------------------------------------------------------------------
In Version 3.1, multi-cycle sequencing was handled using an ad-hoc JavaScript
`switch(this.microStep)` statement with custom state numbers (1 to 6).

In Version 3.2, `CPUPipeline` delegates multi-cycle control entirely to
`MicroSequencer`:
• `tick()` calls `this.microSequencer.step(context)`.
• Control wire generation is driven directly by the active micro-word from the
  Control Store ROM.
• Ad-hoc sequencing is eliminated; every clock cycle directly corresponds to an
  authentic LC-3 micro-state.

--------------------------------------------------------------------------------
C. `cpu/control-unit.js` (Interpreting ROM Micro-Words)
--------------------------------------------------------------------------------
`ControlUnit` interfaces between the Control Store ROM and the physical Datapath.
It reads the active control signals from the current micro-instruction and
converts them into driver assertions (`GatePC`, `GateALU`, `GateMDR`) and latch
enables (`LD.MAR`, `LD.MDR`, `LD.IR`, `LD.PC`, `LD.REG`).

--------------------------------------------------------------------------------
D. `vm.js` (Micro-Step State Telemetry and Dual-Granularity Execution)
--------------------------------------------------------------------------------
`vm.js` exposes the microsequencer's internal state to the runtime environment:
• `vm.uPC`: Getter returning the active micro-program counter state.
• `vm.microSequencer`: Getter granting direct access to the sequencer.
• `vm.tick()`: Executes a single physical clock cycle (advancing uPC by one state).
• `vm.step()`: Runs multiple `vm.tick()` cycles until the microsequencer loops back
  to State 18 (completing an entire macro-instruction).

--------------------------------------------------------------------------------
E. `cpu/instruction-describer.js` & `example.js` (Terminal Visibility)
--------------------------------------------------------------------------------
• `instruction-describer.js` now records and prints the complete micro-path taken
  by the sequencer during macro-instruction execution (e.g. `18 -> 33 -> 35 -> 32 -> 1`).
• `example.js` showcases both granularities:
  1. Micro-Stepping Mode: Manually ticking the clock through States 18, 33, 35, 32,
     and 1 to inspect how the uPC moves through the Control Store ROM.
  2. Macro-Stepping Mode: Executing complete instructions while reporting the
     underlying microcode FSM path and cycle counts.
